# Urtoris iOS App 开发日志

> 项目：Urtoris——工作流双端原型的 iOS 客户端
> 平台：iOS 17+（SwiftUI 原生）· 验证设备：iPhone 17 Pro 模拟器（iOS 27.0）
> 文档版本：v1.0 · 2026-09-19

---

## 1. 项目概况

Urtoris 的 Web 端把「创建工作流」与「使用工作流」拆成两张工作台，再用身份门厅把人送进正确的一张。
iOS 端的目标不是复刻网页的像素，而是让同一套产品关系在手机上成立：

**核心目标**

- 与 Web 端共用 `/api/**`，同一批工作流、同一批运行记录，不做第二套数据
- 视觉严格跟随 `DESIGN.md` 的四张工作台材料，不把使用端的炭黑扩散到其他三面
- 手机上仍然可读、可操作：关键操作 ≥ 44px，默认只保留导航、对话与输入
- 如实区分模拟、真实模型与 n8n，不伪造执行证据

## 4. 接口对齐

iOS 端只使用仓库已有的路由，字段命名与类型严格按服务端返回值解码：

| 路由 | 用途 | iOS 端调用点 |
| --- | --- | --- |
| `GET /api/state?runPage=N` | 工作流、最近运行、分页、是否可信本机 | 门厅与创建端 |
| `POST /api/workflows` | `create` / `save` / `publish` | 创建端命令栏 |
| `DELETE /api/workflows/{id}` | 删除工作流 | 创建端「管理」 |
| `GET /api/consumer/session` | 会话、聊天记录、消息 | 使用端进入时 |
| `PUT /api/consumer/session` | 新建会话 | 使用端「新对话」 |
| `POST /api/agent/chat` | 一轮对话 + 运行证据 | 使用端发送 |

解码层（`Models/WorkflowTypes.swift`）对每个字段都做了宽容处理：
字段缺失或类型变化时退回默认值，一个非关键字段不会让整页失败——
这也是接真实服务端时最先被验证的一点（`archived` 在 `plans` 表里是 0/1 整数）。

## 5. 关键取舍

### 5.1 创建端不搬画布

Web 端创建端是「节点库 + React Flow 画布 + Inspector + 运行面板」的全视口工程台。
手机宽度放不下这三栏，硬塞的结果是三者都不可用。iOS 端改成清单式编排：

- 步骤顺序、类型端口色、1–12 步约束、保存与发布语义全部保留
- 编辑进原生 sheet，等价于 Inspector
- 走同一套 `/api/workflows`，因此草稿与已发布版本仍然是「唯一一份真实来源」

### 5.2 使用端坚持「对话优先」

按 `DESIGN.md` 的 Conversation-First Rule 与 First-Viewport Test：

- 新会话首屏只有会话导航、一个短问题和输入容器，不出现工作流说明卡或状态总览
- Agent 回复不画气泡、不套卡片，只以 30px 头像和排版建立归属
- 用户消息用石墨气泡并在右下收成 4px，保留「这是我说的」方向性
- 路线 / 日志 / 结果全部收进执行详情 sheet，默认不展开

### 5.3 机器人端如实标注能力边界

Web 端通过浏览器 WebRTC 取流。iOS 原生取流需要接入 WebRTC SDK（当前工程不引入第三方依赖），
所以视频窗只显示协议协商结果与连通状态，并明确写出原因；方向控制、官方指令、
七项状态和链路日志全部按官方协议真实收发。
